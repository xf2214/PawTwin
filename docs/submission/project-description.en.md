## Elevator pitch

PawTwin gives a household one traceable care record for each pet. A family member records a measurement or confirms a preference; another member can consult that same context through the App or a labelled Alexa web simulator, take over a confirmed care task and see the result enter the daily report.

## Inspiration and customer problem

Pet care is often a handoff between people. Separate messages can leave a household uncertain about who completed a task, which preference is current and whether a reported number came from a measurement or an assumption. PawTwin explores a shared, per-pet record with accountable authors, explicit permissions and reviewable sources. This is a product hypothesis, not a measured claim about customer outcomes: no real-household trial has been recorded in this development evidence.

## What the working prototype does

- Independent local accounts create or join a household through controlled invitations. Administrator, carer and guest permissions are separate from a member's chosen family label. Changing a label to “Dad” does not grant administrator rights.
- A separate product website introduces the concept at `/`; `/#cases` contains clearly fictional, step-by-step scenarios. `/#app` opens the actual household application and `/#alexa` opens the independent simulator. Website interface previews are illustrative and do not read private household records.
- A top-down pixel room provides access to pet profiles, photos, belongings and care records. Pet characters retain a normal front or side presentation. Each household can keep several local pet profiles; new pets do not inherit the Mochi actuator demo's execution permissions.
- Care tasks support claiming, transfer, completion, postponement, editing and cancellation. Version checks protect concurrent changes; completion records identify the authenticated member.
- Growth records keep actual measurement times, units, source labels, corrections and deletions. Daily and weekly reports calculate values in the household's time zone, show source record IDs and preserve missing values. Dispensed food, food offered and actual intake remain separate facts.
- A pet context combines profile facts, measured growth, owner-confirmed memory, recent observations and reference metadata. The App and Alexa web simulator read the same context. Candidate memories require confirmation; deleted or expired records stop entering new answers.
- The simulator accepts typed speech-like questions and shortcuts. It exposes each answer's source IDs, context version and backend; a new session clears the current page's conversation while retaining household records. It keeps at most 20 turns in page memory; leaving, refreshing or changing pet/account clears them. Optional browser speech synthesis reads a reply without recording microphone input.
- An explicit care request such as “Arrange play” forms a rule-based draft. The member checks its type/title and chooses a concrete time, prepares a pending proposal, then explicitly confirms it. Only confirmation creates a manual task; stale context is rejected. Completion requires a person to perform the care and record it. Natural-language date parsing, autonomous scheduling and real device execution are not demonstrated by this flow.

## How it is built

The local product uses Python 3.12, FastAPI/Uvicorn, Pydantic contracts, SQLite, Python `zoneinfo` with pinned `tzdata`, and a React/TypeScript/Vite frontend. It targets **one application instance with local file-backed data**, not a distributed household cloud service. Accounts use salted `scrypt` password hashes. Server-side sessions, CSRF checks, current household membership and pet scope govern access. Reports are generated by a background worker with persistent progress, retry and rebuild behavior.

The core demonstration follows **record → confirm → consult shared context → confirm a manual care task → another member completes it → report updates**. An answer or memory never grants permission, fills a missing measurement or overrides a hard device limit.

## Demonstration and evidence

The existing two-account browser rehearsal uses real local API calls. It records 1.20 kg on 25 September and 1.35 kg on 2 October, explicitly labelled demonstration samples. The computed change is **150 g, 12.5%, across seven actual days**. The earlier measurement is the comparison baseline before the report's weekly window; the demonstration does not claim both measurements are inside that window.

The completed current rehearsal shows the product website and independent `/#alexa` simulator. The owner confirms a feather-toy preference; another member asks in a new simulator session. A care request then proceeds through draft, time selection, preparation, explicit confirmation, manual completion and a daily report. After deletion, a fresh answer stops citing the preference. The rehearsal checks source IDs, the actual completing account and `manual_care` provenance. ## Challenges and what we learned

The documented implementation review found issues in shared-entry writes, historical report cutoffs, retry behavior, stale proposal confirmation, author snapshots and delayed responses after a pet switch. The fixes added behavioral regressions rather than hiding these cases in presentation material. The prototype treats accountable handoffs, record validity and deterministic statistics as requirements for a credible pet context. See the [review and repair record](../reviews/EXT-local-review-2026-10-03.md) and [tool feedback and friction log](product-feedback.en.md).

The 11 October workbench review additionally repaired a quota race between different feeding runs through a persisted owner feeding gate, guarded delayed facts reevaluation with compare-and-set, and committed receipt/accounting/terminal state atomically. Unknown receipts and interrupted execution retain the gate. Authentication throttling now uses the server-resolved client address instead of raw `X-Forwarded-For`; the local launch explicitly disables proxy-header rewriting. [Local safety regressions](../../tests/test_feeding_reservation.py) cover these behaviors. [DynamoDB transaction-shape tests](../../tests/test_feeding_dynamo_offline.py) are offline only; old facts without a guard version fail closed. No live DynamoDB outcome follows from them.

Memory remains owner-confirmed SQLite data. The product does not translate animal language, diagnose illness, establish proven hunger prediction or infer intake from dispensing.
